# Implement task

Executes one task at a time from a feature's already-approved `plan.md` and `tasks.md` (generated by [[plan-and-task-generator]]), applying this project's development conventions and a fixed set of code-quality checks before considering the task done. This skill only implements, it never plans and never certifies, [[verify-tasks]] still does the evidence-based reconciliation and box-checking afterward.

## Scope

- Reads: the feature's approved `plan.md` and `tasks.md`, `/AGENTS.md`, the existing codebase (components, data files, `main.css` tokens) to check for patterns to reuse before writing new ones.
- Writes: the application code/content each task describes. Never marks or unmarks any checkbox in `tasks.md`, checking off tasks is `verify-tasks`' job, not this skill's, so it can independently audit real evidence rather than trust this skill's own report of what it did. Never edits `spec.md` or `constitution.md`, that's `close-feature`'s job. Never writes `plan.md` or `tasks.md` themselves, that's `plan-and-task-generator`'s job.

Only runs when explicitly invoked as `/implement-task <feature-name> execute`. Each invocation implements exactly one task, then ends its turn completely. The next task never starts because the agent interpreted a conversational reply ("dale", "sigue", "se ve bien") as a go-ahead, it starts only because the user ran `execute` again, the same mechanical, explicit-argument checkpoint used for moving from `plan-and-task-generator` to this skill in the first place.

## Step 1 — Confirm the precondition

Read `tasks.md` and `plan.md`. Since this skill never checks boxes itself, don't trust checkbox state to know what's already done, a box may be unchecked even after real work happened in an earlier invocation. Instead, look at the actual code/git state the same way `verify-tasks` gathers evidence, to find which tasks already have real, verifiable work behind them and which don't. If anything looks stale or inconsistent with `spec.md` or a changed plan, stop and ask rather than assuming the plan is still accurate.

## Step 2 — Look for existing patterns before writing new code

Before implementing, search the codebase for a component, function, or data pattern that already does something similar to what this task needs. Reusing or extending an existing pattern is preferred over writing a parallel one from scratch, this is the DRY check applied proactively, not just after the fact.

## Step 3 — Implement the task

Take the next task without real evidence of completion (per Step 1). Implement it, applying these checks before considering it done:

- **DRY** — no block of logic or JSX duplicated from what already exists elsewhere in the codebase (per Step 2) or duplicated within the new code itself. Extract a shared piece instead of copying it.
- **Single responsibility** — the component or function built for this task does one clear thing. If it's taking on responsibilities beyond what this task describes, split it rather than let it grow overloaded.
- **Typing** — new props and state are explicitly typed, following the existing patterns in `client/data/types.ts` and sibling components, not left implicit.
- **No hardcoded values** — reuse the design tokens and constants already established in `main.css` and `client/data/`, per `/AGENTS.md`. Don't introduce a new literal (color, spacing, string) where an existing token or constant already covers it.
- **Naming conventions** — match the naming style already used by sibling components and data files (English identifiers, existing casing patterns), including prefixing event handlers with `handle` (`handleClick`, `handleSubmit`) where the codebase already follows that pattern. Don't introduce a new convention for this task alone.
- **Avoid unnecessary re-renders** — static data or objects that don't depend on props or state are defined outside the component body, not recreated on every render inside it.
- **Readability** — prefer early returns over deeply nested conditionals where the existing codebase already follows that pattern, don't introduce a new control-flow style for this task alone.
- **No leftover work** — no TODO comments, placeholder text, or incomplete pieces left behind when the task is described as done, per the constitution's Maintainability principle. If something is intentionally left for a later task, say so explicitly in Step 4 rather than leaving a silent gap.
- **Accessibility** — interactive elements (links, buttons, the floating WhatsApp button, form-like controls if any) get correct `aria-label`/`alt` attributes and stay reachable and operable via keyboard, not only mouse or touch.

## Step 4 — Describe and stop

Describe what changed, in enough detail to be reviewed against `plan.md` and the source content, including a plain note on how the Step 3 checks were satisfied (or, if one couldn't be fully satisfied, say so explicitly rather than silently skip it). This description is the user's real checkpoint, not the checklist. Then stop this invocation entirely. Do not implement a second task in the same run.

## Step 5 — Report when nothing is left

When an `execute` invocation's Step 1 finds no implementation task left without evidence, don't implement anything, say so plainly instead. Note that every checkbox in `tasks.md` is still unset because this skill never checks them, and name the next steps in order: `verify-tasks` to certify each task against evidence and check it off, then `/analyze-test-cases <feature-name>` to propose test cases, the user confirms them in `test-plan.md`, `/write-tests <feature-name>` to write and run them, and `review-tests` as the final audit before `close-feature`.
